===============================================================================
  RTL FIX ADVISOR — SURGICAL CORRECTION GUIDANCE
===============================================================================
  Root Cause     : PROTOCOL/SCHEDULING_CANCELLATION
  Primary Signal : target signal
  Rule           : AXI4L_WRITE_RESPONSE_MISSING  (AXI4-Lite Spec §A3.2.1)
  Cycle          : 1312
===============================================================================

  0. Detected RTL Pattern
  -------------------------------------------------------------------------------
    Location   : the always-block
    Faulty RTL : target signal <= 0;               // D2: broad — overwrites D1
    if ((ARESETn) && (write_state == RESP)) target signal <= 1; // D1: specific — LOST to D2
    Issue      : D2 (broad) executes after D1 (specific) in the same delta — D1's assignment is always overwritten by D2.

    Recommended fix:
    if ((ARESETn) && (write_state == RESP)) target signal <= 1;   // D1: specific — evaluated first
    else              target signal <= 0;   // D2: default — only when D1 does not fire

  1. Design Mistake
  -------------------------------------------------------------------------------
    The RTL always-block contains two drivers for target signal. The enabling
    driver (D1) correctly asserts target signal=1 under condition `(ARESETn)
    && (write_state == RESP)`. However, a later driver (D2) assigns target
    signal=0 under `((ARESETn) && (write_state == RESP)) && (BREADY)`, which
    is a superset of `(ARESETn) && (write_state == RESP)`. Because D2 is
    evaluated after D1 in the same always-block, D2's assignment always wins,
    making target signal permanently stuck at 0 whenever `(ARESETn) &&
    (write_state == RESP)` is true.

  2. Safe Design Rule Violated
  -------------------------------------------------------------------------------
    RTL coding rule: within a single always-block, never assign a signal in a
    broader condition after assigning it in a narrower sub-condition that
    must take precedence. Priority must flow from most-specific (narrowest
    condition) to least-specific (broadest condition), with the most-specific
    assignment appearing LAST so it wins. Alternatively, structure the
    conditions as mutually exclusive branches using if-else chains.

  3. Correction Strategy
  -------------------------------------------------------------------------------
    Option A — Reorder assignments: place the specific enabling assignment
    (D1) AFTER the default/broad assignment (D2). The specific case overrides
    the default.
    Option B — Use if-else to make the conditions mutually exclusive:
    restructure the code so that `(ARESETn) && (write_state == RESP)` is in
    an else-if branch that is only reached when `((ARESETn) && (write_state
    == RESP)) && (BREADY)` does not override it.
    Option C — Merge conditions: combine D1 and D2 into a single expression
    that computes the correct output in one assignment.
    Do NOT add a separate always-block for target signal — that would create
    a race condition.

  4. Guarded-Code Example
  -------------------------------------------------------------------------------
    // BEFORE (defective — D2 overwrites D1):
    always_ff @(posedge ACLK or negedge ARESETn) begin
        if (!ARESETn) target signal <= 0;
        else begin
            target signal <= 0; // D2: broad condition (always active in
            IDLE)
            if ((ARESETn) && (write_state == RESP)) target signal <= 1; //
            D1: specific (IDLE && ARVALID) — OVERWRITTEN by D2
        end
    end

    // AFTER — Option A (reorder: D1 last = highest priority):
    always_ff @(posedge ACLK or negedge ARESETn) begin
        if (!ARESETn) target signal <= 0;
        else begin
            if ((ARESETn) && (write_state == RESP)) target signal <= 1; //
            D1: specific case — evaluated first
            else target signal <= 0; // D2: default — only when D1 does not
            apply
        end
    end

    // AFTER — Option B (if-else, mutually exclusive):
    always_ff @(posedge ACLK or negedge ARESETn) begin
        if (!ARESETn)
            target signal <= 0;
        else if ((ARESETn) && (write_state == RESP)) // specific condition
        takes priority
            target signal <= 1;
        else if (((ARESETn) && (write_state == RESP)) && (BREADY)) // broad
        default — only when specific does not apply
            target signal <= 0;
    end

  5. Why This Fix Removes the Failure
  -------------------------------------------------------------------------------
    Option A restores correct NBA (non-blocking assignment) semantics: the
    last write within a single delta wins, and D1 (specific) is now the last
    write when `(ARESETn) && (write_state == RESP)` is true. D2 (broad) only
    takes effect when D1 does not apply. The masking mechanism is eliminated
    by construction. Under Option B, the if-else structure makes the
    conditions structurally exclusive — it is impossible for both branches to
    fire in the same delta.

  6. Tradeoffs
  -------------------------------------------------------------------------------
    - Option A: zero area and timing impact. Risk: requires careful review of
    all drivers for {sig} to ensure no other broad-before-specific ordering
    exists.
    - Option B: slightly more verbose but more readable and tool-friendly for
    coverage measurement (each branch is an independent coverpoint).
    - Option C: reduces code lines but may obscure intent for reviewers;
    prefer A or B.
    - All options: run regression and check that ARREADY (or the affected
    signal) deasserts correctly on reset and after the transaction completes
    — the fix must not prevent the default-low behavior for other states.
