===============================================================================
  RTL FIX ADVISOR — SURGICAL CORRECTION GUIDANCE
===============================================================================
  Root Cause     : PROTOCOL/TEMPORAL_VIOLATION
  Primary Signal : RDATA
  Rule           : AXI4L_BVALID_PERSISTENCE  (AXI4-Lite Spec §A3.1.2)
  Cycle          : 14672
===============================================================================

  0. Detected RTL Pattern
  -------------------------------------------------------------------------------
    Location   : the always-block
    Faulty RTL : RDATA <= 0;               // D2: broad — overwrites D1
    if (enabling condition) RDATA <= 1; // D1: specific — LOST to D2
    Issue      : D2 (broad) executes after D1 (specific) in the same delta — D1's assignment is always overwritten by D2.

    Recommended fix:
    if (enabling condition) RDATA <= 1;   // D1: specific — evaluated first
    else              RDATA <= 0;   // D2: default — only when D1 does not fire

  1. Design Mistake
  -------------------------------------------------------------------------------
    The RTL always-block contains two drivers for RDATA. The enabling driver
    (D1) correctly asserts RDATA=1 under condition `enabling condition`.
    However, a later driver (D2) assigns RDATA=0 under `superset condition`,
    which is a superset of `enabling condition`. Because D2 is evaluated
    after D1 in the same always-block, D2's assignment always wins, making
    RDATA permanently stuck at 0 whenever `enabling condition` is true.

  2. Safe Design Rule Violated
  -------------------------------------------------------------------------------
    RTL coding rule: within a single always-block, never assign a signal in a
    broader condition after assigning it in a narrower sub-condition that
    must take precedence. Priority must flow from most-specific (narrowest
    condition) to least-specific (broadest condition), with the most-specific
    assignment appearing LAST so it wins. Alternatively, structure the
    conditions as mutually exclusive branches using if-else chains.

  3. Correction Strategy
  -------------------------------------------------------------------------------
    Option A — Reorder assignments: place the specific enabling assignment
    (D1) AFTER the default/broad assignment (D2). The specific case overrides
    the default.
    Option B — Use if-else to make the conditions mutually exclusive:
    restructure the code so that `enabling condition` is in an else-if branch
    that is only reached when `superset condition` does not override it.
    Option C — Merge conditions: combine D1 and D2 into a single expression
    that computes the correct output in one assignment.
    Do NOT add a separate always-block for RDATA — that would create a race
    condition.

  4. Guarded-Code Example
  -------------------------------------------------------------------------------
    // BEFORE (defective — D2 overwrites D1):
    always_ff @(posedge ACLK or negedge ARESETn) begin
        if (!ARESETn) RDATA <= 0;
        else begin
            RDATA <= 0; // D2: broad condition (always active in IDLE)
            if (enabling condition) RDATA <= 1; // D1: specific (IDLE &&
            ARVALID) — OVERWRITTEN by D2
        end
    end

    // AFTER — Option A (reorder: D1 last = highest priority):
    always_ff @(posedge ACLK or negedge ARESETn) begin
        if (!ARESETn) RDATA <= 0;
        else begin
            if (enabling condition) RDATA <= 1; // D1: specific case —
            evaluated first
            else RDATA <= 0; // D2: default — only when D1 does not apply
        end
    end

    // AFTER — Option B (if-else, mutually exclusive):
    always_ff @(posedge ACLK or negedge ARESETn) begin
        if (!ARESETn)
            RDATA <= 0;
        else if (enabling condition) // specific condition takes priority
            RDATA <= 1;
        else if (superset condition) // broad default — only when specific
        does not apply
            RDATA <= 0;
    end

  5. Why This Fix Removes the Failure
  -------------------------------------------------------------------------------
    Option A restores correct NBA (non-blocking assignment) semantics: the
    last write within a single delta wins, and D1 (specific) is now the last
    write when `enabling condition` is true. D2 (broad) only takes effect
    when D1 does not apply. The masking mechanism is eliminated by
    construction. Under Option B, the if-else structure makes the conditions
    structurally exclusive — it is impossible for both branches to fire in
    the same delta.

  6. Tradeoffs
  -------------------------------------------------------------------------------
    - Option A: zero area and timing impact. Risk: requires careful review of
    all drivers for {sig} to ensure no other broad-before-specific ordering
    exists.
    - Option B: slightly more verbose but more readable and tool-friendly for
    coverage measurement (each branch is an independent coverpoint).
    - Option C: reduces code lines but may obscure intent for reviewers;
    prefer A or B.
    - All options: run regression and check that ARREADY (or the affected
    signal) deasserts correctly on reset and after the transaction completes
    — the fix must not prevent the default-low behavior for other states.
